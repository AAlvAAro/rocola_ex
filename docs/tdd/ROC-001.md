# ROC-001: Admin device picker

## Summary
The host opens `/admin` to see their Spotify Connect devices, picks one to play on, and refreshes the list. Restricted devices (`is_restricted: true`) show as unavailable and never get commands. The check happens in `Rocola.Jukebox`, not just in the adapter (rule 6).

## Current code
- `lib/rocola/spotify.ex`: the behaviour. It already defines `devices/0 :: {:ok, [device]} | {:error, term}` and `transfer_playback/1 :: :ok | {:error, term}`, plus delegating functions that pick the adapter from `config :rocola, :spotify`. The `device` type is `%{id, name, is_active, is_restricted}`.
- `lib/rocola/spotify/fake.ex`: an Agent with 2 seeded devices: `fake-living-room` (available) and `fake-locked` (restricted). `transfer_playback/1` returns `{:error, :device_not_found}` for an unknown id and `{:error, :restricted_device}` for a restricted one; on success it makes only that device `is_active`. `reset/0` restores the seed. There is no way to change the device list or see which commands came in.
- `lib/rocola/spotify/web.ex`: stub. `devices/0` and `transfer_playback/1` return `{:error, :not_implemented}`.
- `lib/rocola/jukebox/`: doesn't exist yet. There is no `Rocola.Jukebox` context.
- `lib/rocola_web/router.ex`: the `:browser` scope only has `get "/"`. There is no `live` route and no `lib/rocola_web/live/` directory.
- `lib/rocola/application.ex`: starts `Rocola.Spotify.Fake` unconditionally (left as is here).
- `test/rocola/spotify/fake_test.exs`: covers search, the restricted-transfer rejection and add-only queueing.
- `docs/adr/001-architecture.md`: Spotify sits behind the behaviour, and the Fake mirrors real limits. Nothing in this ticket changes those decisions.

## Design

### Spotify behaviour (no new callback)
The two capabilities this ticket needs, `devices/0` and `transfer_playback/1`, are already callbacks with a Fake implementation and a Web stub. So rule 3 is already met and no callback is added. The `Web` stub stays `{:error, :not_implemented}`. The real call (`GET /v1/me/player/devices`, `PUT /v1/me/player`) is out of scope.

### Fake test seams (`lib/rocola/spotify/fake.ex`)
These are not behaviour callbacks. They are test/dev helpers like the existing `reset/0`:
- `@spec put_devices([Rocola.Spotify.device()] | {:error, term}) :: :ok`: replaces the device list. The `{:error, reason}` form makes `devices/0` return that error, which simulates Spotify being unreachable.
- `@spec commands() :: [{:transfer_playback, String.t()}]`: every `transfer_playback/1` call the Fake *received*, in order, rejected ones included. Tests use it to prove that the context never sent a command to a restricted device.
- Agent state gains `devices_error: nil | term` and `commands: []`. `reset/0` clears both. Existing behaviour doesn't change: the Fake still rejects restricted devices itself, as the real API does.

### Context `Rocola.Jukebox` (`lib/rocola/jukebox.ex`)
This is the entry module for the context. Queue rules and rate limits will go into `lib/rocola/jukebox/` in later tickets.
- `@spec list_devices() :: {:ok, [Rocola.Spotify.device()]} | {:error, term}`: calls `Rocola.Spotify.devices/0`. Available devices come first, then by name.
- `@spec select_device(String.t()) :: :ok | {:error, :restricted_device | :device_not_found | term}`: fetches `Rocola.Spotify.devices/0` and looks up the id:
  - not found: `{:error, :device_not_found}`, no command sent;
  - `is_restricted: true`: `{:error, :restricted_device}`, **no command sent** (rule 6);
  - otherwise: `Rocola.Spotify.transfer_playback(id)`, and its result is passed back.
  - If `devices/0` fails, that error is passed back and no command is sent.

### LiveView `RocolaWeb.AdminLive` (`lib/rocola_web/live/admin_live.ex`)
- Route: `live "/admin", AdminLive` in the existing `:browser` scope.
- `mount/3`: assigns `devices` (a list) and `error` (`nil | term`) from `Jukebox.list_devices/0`.
- Render (inside `<Layouts.app flash={@flash}>`): one row per device with `id="device-#{id}"`.
  - Available: a "Play here" button with `phx-click="select"` and `phx-value-id={id}`. If the device is active, it gets a "Playing here" badge instead of the button.
  - Restricted: greyed out, an "Unavailable" label, and a disabled button with no `phx-click`.
  - Empty list: the hint "No devices found. Open Spotify on a speaker or phone, then refresh."
  - `@error` set: an error message ("Couldn't reach Spotify") and the empty list.
  - A "Refresh" button with `phx-click="refresh"`.
- Events:
  - `handle_event("refresh", _params, socket)`: reloads with `Jukebox.list_devices/0`.
  - `handle_event("select", %{"id" => id}, socket)`: calls `Jukebox.select_device(id)`. On `:ok`, reloads the devices and flashes info "Playing on <name>". On `{:error, :restricted_device}`, flashes error "That device can't be controlled". On `{:error, :device_not_found}`, flashes error "Device is gone, refresh". On any other error, flashes a generic error. A restricted id is still refused even if a client forges the event, because the guard is in the context.
- The LiveView calls only `Rocola.Jukebox`. It never calls `Rocola.Spotify`, an adapter, `Req` or `Repo` (rule 2).

### Migration
None. The active device is Spotify's state (`is_active`), so there is nothing to persist.

## Tests first
`test/rocola/spotify/fake_test.exs` (add):
1. `put_devices/1` replaces the device list, and `reset/0` restores the seeded two devices and empties `commands/0`.
2. `put_devices({:error, :unavailable})` makes `devices/0` return `{:error, :unavailable}`.

`test/rocola/jukebox_test.exs` (new, `async: false`, `Fake.reset/0` in setup):
3. `list_devices/0` returns both seeded devices with the available one first and `is_restricted` kept.
4. `select_device("fake-living-room")` returns `:ok`, and `list_devices/0` then shows it as `is_active`.
5. `select_device("fake-locked")` returns `{:error, :restricted_device}` and `Fake.commands()` is `[]`.
6. `select_device("nope")` returns `{:error, :device_not_found}` and `Fake.commands()` is `[]`.
7. `select_device/1` passes back a `devices/0` error and sends no command.

`test/rocola_web/live/admin_live_test.exs` (new, `ConnCase`, `async: false`, `Fake.reset/0` in setup):
8. `/admin` lists both device names.
9. The restricted device row shows "Unavailable" and its button is disabled with no `phx-click`.
10. Clicking "Play here" on the living room shows "Playing here" and the info flash.
11. A forged `select` event with `fake-locked` shows the error flash and `Fake.commands()` stays `[]`.
12. After `Fake.put_devices/1` adds a device, clicking "Refresh" shows it.
13. With `Fake.put_devices({:error, :unavailable})`, the page shows "Couldn't reach Spotify" and doesn't crash.
14. With `Fake.put_devices([])`, the page shows the "No devices found" hint.

## Out of scope
- The real `Web` adapter, `TokenServer`, and the Spotify OAuth login.
- Authentication for `/admin` (see Risks / open question).
- Polling or PubSub auto-refresh of devices (refresh is manual).
- Volume, play/pause, or skip controls.
- Persisting a "preferred device" across restarts.
- Starting the Fake only in dev/test from `application.ex`.

## Risks
- **`/admin` is open to anyone on the LAN**, including guests who scanned the QR. The worst a guest can do is switch the speaker. Possible fix in a follow-up: `Plug.BasicAuth` (part of Plug, no new dependency) with a password from `runtime.exs` env. Open question for the host.
- **Device list goes stale**: Spotify drops idle devices, so a listed device can be gone by the time the host clicks it. This is handled by `:device_not_found` plus the "refresh" flash. The real API also returns 404 for that, which the `Web` adapter will need to map.
- **Race between the check and the transfer**: a device could become restricted between `devices/0` and `transfer_playback/1`. This is acceptable because the adapter (Fake and the real API) rejects it too.
- **`async: false` everywhere** because the Fake is a single named Agent. This is fine at the current size.
- The Fake command log could grow without limit in a long dev session. It is small (one tuple per click) and cleared by `reset/0`.

## Product review
Decision: APPROVED
- Delivers the host story end to end: list, "Play here", "Playing here" badge, manual Refresh, restricted shown as "Unavailable" and refused in the context.
- Edge cases a host hits are covered: empty list hint, Spotify unreachable, stale device, forged select.
- Scope is tight: no extra controls, no persistence, nothing commercial or multi-venue.
- Leaving `/admin` auth out is acceptable here: no guest QR page exists yet, and the worst a guest can do is switch the speaker.
- Required follow-up: add a roadmap ticket for `Plug.BasicAuth` on `/admin`, to ship before or with ROC-002 (guest QR).
